Hard Block Rules (Instant Rejection)

These rules immediately reject the transaction

Rule ID Rule Name What It Detects Example Scenario Why This Rule Exists
F1 Velocity Limit Exceeded Too many transactions in 10 minutes (5+ for most tiers, 2/hour for HIGH_VALUE) Example: User sends 6 payments in 10 minutes to different people Automated fraud scripts send many transactions rapidly. Normal humans don't make 5+ payments in 10 minutes.
F3 Dormant Account Spike Account inactive >30 days suddenly sends >₹500 Example: Account unused since December suddenly sends ₹5,000 in January Compromised accounts often show sudden activity after long dormancy. Attackers wait for victims to forget about old accounts.
F7 Untrusted Receiver High Value (P2P Only) Sending >₹5,000 to a complete stranger (trust depth = 0) Example: First-time user tries to send ₹50,000 to unknown person Social engineering scams trick users into sending large amounts to strangers. Trust must be built first.
F18 Daily Per-Receiver Limit P2P: >₹1,00,000/day per receiver
Merchant: >₹3,00,000/day per receiver		 Example: User already sent ₹80,000 to friend today, tries to send ₹30,000 more Limits prevent catastrophic loss from compromised accounts. Even if hacked, maximum loss is capped.
F29 Geo-Velocity Violation Transaction from location >500km away within time that makes it impossible (>900 km/h) Example: Login from Mumbai, then 10 minutes later transaction from Delhi (1,400 km = 8,400 km/h) Impossible travel indicates VPN evasion or device spoofing. No human can travel faster than planes.
F30 Merchant Location Fraud Sender's registered city doesn't match merchant's registered location Example: User in Mumbai sends payment to a merchant registered in a different city with no prior interaction Fraudsters use merchant accounts in different cities to launder money. Location mismatch is a strong fraud signal.
